# 知识库与目录规划

## 1. 目标

本文件用于统一项目后续的：

- 多岗位知识库目录结构
- 主库与补充库分层规则
- 命名规范
- collection 规划

目标是让后续新增岗位时可以复用现有 Java RAG 方案，而不是每个岗位都重做一套。

---

## 2. 总体目录建议

推荐目录结构如下：

```text
data/
├─ java_backend/
│  ├─ Java后端主知识库-标准化面试题库.md
│  ├─ Java后端主知识库格式规范.md
│  ├─ Java后端补充知识库格式规范.md
│  └─ support/
├─ web_frontend/
│  ├─ Web前端主知识库-标准化面试题库.md
│  ├─ Web前端主知识库格式规范.md
│  ├─ Web前端补充知识库格式规范.md
│  └─ support/
└─ shared/
   └─ behavioral/
```

---

## 3. 岗位目录设计

每个岗位目录建议至少包含：

- 1 份主知识库
- 1 份主知识库格式规范
- 1 份补充知识库格式规范
- 1 个 `support/` 目录存放补充资料

### 主知识库

职责：

- 定义题目
- 定义标准回答
- 定义追问点
- 定义评分点
- 定义常见失分点

### 补充知识库

职责：

- 提供原理补充
- 提供项目案例
- 提供故障排查与性能优化素材

---

## 4. 推荐命名规范

### 主知识库文件

格式：

- `<岗位名称>主知识库-标准化面试题库.md`

示例：

- `Java后端主知识库-标准化面试题库.md`
- `Web前端主知识库-标准化面试题库.md`

### 主知识库规范文件

格式：

- `<岗位名称>主知识库格式规范.md`

### 补充知识库规范文件

格式：

- `<岗位名称>补充知识库格式规范.md`

### 补充知识库文章

格式：

- `<主题>-<内容概述>补充.md`

示例：

- `集合-HashMap与ConcurrentHashMap补充.md`
- `并发-volatile与线程池补充.md`
- `CSS-布局与响应式补充.md`

---

## 5. collection 规划

建议一开始就按“岗位 + 分层”管理 collection。

### Java 后端

- `java_interview_main`
- `java_interview_support`

### Web 前端

- `frontend_interview_main`
- `frontend_interview_support`

### 行为题共享库

- `shared_behavioral_main`

---

## 6. 为什么不建议全塞进一个 collection

如果主库、补充库、规范文档、杂项文章混在一起，会有这些问题：

- 出题检索不稳定
- 标准答案检索被长文污染
- 评分点难以精准命中
- 追问生成容易偏题

因此建议分层：

- 主库负责问、答、评
- 补充库负责深、细、广

---

## 7. 第二岗位建议

当前最推荐新增的第二岗位是：

- `Web 前端`

原因：

- 与 Java 后端差异足够明显
- 评委更容易感受到“岗位化”的产品价值
- 前端与后端可以共用平台框架，但题库和评估标准差异明显

前端主库建议优先覆盖：

- HTML/CSS/JavaScript 基础
- 浏览器原理
- 网络与性能优化
- React 或 Vue
- 工程化与打包
- 项目经验深挖
- 场景题
- 行为题

---

## 8. shared 目录建议

后续可以新增 `data/shared/`，存放跨岗位通用资料：

- 行为题
- 通用沟通表达建议
- 通用面试礼仪与表达建议
- 通用报告模板素材

这些内容不必绑定单一岗位，但要避免与技术主库混淆。

---

## 9. 与后端接口的关系

后续接口层可直接依赖这个目录结构：

- 根据 `role` 选择岗位目录
- 根据 `knowledge_base_type` 选择主库或补充库
- 根据 `collection_name` 执行检索

也就是说，目录结构规范越早定下来，后面服务层越容易做。

---

## 10. 当前建议的落地动作

下一阶段建议按下面顺序推进：

1. 保持 Java 目录不再随意改名
2. 为 Java 补充库准备 `support/` 子目录
3. 新建 Web 前端岗位目录
4. 复制并改造主库规范
5. 开始构建第二岗位主知识库
