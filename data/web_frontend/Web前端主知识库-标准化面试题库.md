## Q001 JavaScript 数据类型与类型判断

### 元数据
- 岗位：Web前端开发工程师
- 题型：技术知识
- 主题：前端基础
- 难度：初级
- 关键词：`JavaScript` `数据类型` `typeof` `instanceof`

### 面试题
请你讲一下 JavaScript 的常见数据类型，以及常用的类型判断方式。

### 标准回答
JavaScript 常见数据类型可以分为基本类型和引用类型。基本类型通常包括 `number`、`string`、`boolean`、`undefined`、`null`、`symbol` 和 `bigint`；对象、数组、函数等通常归为引用类型。类型判断常见方法有 `typeof`、`instanceof`、`Array.isArray()` 和 `Object.prototype.toString.call()`。其中 `typeof` 适合判断基础类型和函数，但对 `null` 会返回 `object`；`instanceof` 更适合判断对象原型链关系；如果想更稳定地区分数组、对象、日期等类型，通常会用 `Object.prototype.toString.call()`。

### 追问点
- 为什么 `typeof null` 的结果是 `object`？
- `instanceof` 的底层判断逻辑是什么？
- 为什么判断数组时通常不推荐只用 `typeof`？

### 评分点
- 能区分基本类型和引用类型
- 能说明不同类型判断方式的适用场景
- 能指出 `typeof null` 这个常见陷阱

### 常见失分点
- 漏掉 `symbol` 或 `bigint`
- 说 `typeof` 可以精确判断所有对象类型

## Q002 闭包与作用域链

### 元数据
- 岗位：Web前端开发工程师
- 题型：技术知识
- 主题：前端基础
- 难度：中级
- 关键词：`闭包` `作用域链` `内存泄漏` `函数`

### 面试题
什么是闭包？闭包有哪些常见使用场景和风险？

### 标准回答
闭包本质上是函数与其定义时所在词法作用域的组合。即使外层函数已经执行结束，内部函数依然可以访问外层作用域中的变量。常见使用场景包括封装私有变量、函数工厂、事件回调和异步逻辑等。闭包本身不是问题，风险主要在于如果长期持有不再需要的大对象或 DOM 引用，可能导致内存不能及时释放，从而带来内存泄漏或状态难以维护的问题。因此在工程实践里，既要会用闭包实现封装，也要注意生命周期管理。

### 追问点
- 闭包为什么能够访问外层变量？
- 闭包一定会造成内存泄漏吗？
- 在前端框架里闭包常见于哪些位置？

### 评分点
- 能说清闭包定义
- 能结合作用域链解释原因
- 能讲出场景和风险，而不是只背概念

### 常见失分点
- 把闭包简单等同于“函数套函数”
- 说闭包一定会导致内存泄漏

## Q003 浏览器从输入 URL 到页面展示经历了什么

### 元数据
- 岗位：Web前端开发工程师
- 题型：技术知识
- 主题：浏览器
- 难度：中级
- 关键词：`浏览器` `URL` `DNS` `HTTP` `渲染`

### 面试题
请你描述一下，从浏览器输入一个 URL 到最终页面展示，中间大致经历了哪些过程？

### 标准回答
整体流程通常包括：先进行 URL 解析，判断协议并补全信息；然后查找缓存并进行 DNS 解析，拿到目标服务器 IP；接着建立 TCP 连接，如果是 HTTPS 还要进行 TLS 握手；之后浏览器发送 HTTP 请求，服务器返回响应内容。拿到 HTML 后，浏览器会解析文档并构建 DOM Tree，同时解析 CSS 构建 CSSOM，再结合生成 Render Tree，随后进行布局和绘制。如果过程中遇到脚本，某些脚本执行还可能阻塞解析。页面加载完成后，可能还会继续加载异步资源、执行事件回调和交互逻辑。

### 追问点
- DNS 解析和缓存一般有哪些层级？
- 为什么 CSS 会影响渲染，而 JavaScript 可能阻塞解析？
- 重排和重绘分别是什么？

### 评分点
- 能覆盖网络请求和浏览器渲染两个阶段
- 能说明 HTTPS、DOM、CSSOM、布局绘制等关键环节
- 回答有流程感，层次清晰

### 常见失分点
- 只回答网络请求，不回答渲染过程
- 把重绘和重排混为一谈

## Q004 React 中 state 更新为什么是异步感知的

### 元数据
- 岗位：Web前端开发工程师
- 题型：技术知识
- 主题：React
- 难度：中级
- 关键词：`React` `state` `批处理` `渲染`

### 面试题
在 React 中，为什么我们经常会感觉 `state` 更新不是立刻生效的？

### 标准回答
React 中的 `state` 更新并不等同于“同步立刻改完并重新渲染”。为了提升性能和保证渲染调度的可控性，React 会对多次状态更新做批处理，把更新请求先收集起来，再在合适的时机统一计算并触发渲染。所以在同一个事件回调里，刚调用完 `setState` 或状态更新函数后立即读取，拿到的可能还是当前这一轮渲染的旧值。更准确地说，不是 state 没变，而是组件重新渲染和拿到新快照发生在后续调度阶段。理解这一点有助于避免因为直接依赖旧闭包值而写出错误逻辑。

### 追问点
- 什么是批处理更新？
- 为什么函数式更新能避免部分旧值问题？
- React 事件和原生事件里的表现有什么差异？

### 评分点
- 能说明“异步感知”背后的调度原因
- 能提到批处理或渲染快照概念
- 能结合开发中的常见误区解释

### 常见失分点
- 直接说 React 的 state 就是异步的
- 解释不到渲染调度和批处理层

## Q005 前端性能优化可以从哪些方向入手

### 元数据
- 岗位：Web前端开发工程师
- 题型：场景题
- 主题：前端性能优化
- 难度：中级
- 关键词：`性能优化` `首屏` `懒加载` `缓存` `代码分割`

### 面试题
如果一个前端页面首屏加载很慢，你一般会从哪些方向去分析和优化？

### 标准回答
前端性能优化通常要从网络、资源、渲染和代码执行几个维度综合看。网络层面可以看接口耗时、资源体积、缓存命中、是否启用压缩和 CDN；资源层面可以做图片压缩、字体优化、按需加载和代码分割；渲染层面可以减少不必要的重排重绘，优化关键渲染路径；代码层面可以减少首屏不必要的逻辑执行，延后低优先级任务。真正落地时，不能只说“做缓存、做懒加载”，而是要先借助性能面板、埋点指标或 Web Vitals 找到瓶颈，再有针对性优化并验证收益。

### 追问点
- 代码分割和懒加载分别解决什么问题？
- 如何判断瓶颈是在接口、资源还是渲染？
- 你会关注哪些性能指标？

### 评分点
- 能从多个维度系统分析问题
- 能体现“先定位再优化”的思路
- 能结合具体手段说明

### 常见失分点
- 只会泛泛说“开缓存、压图片”
- 没有性能定位方法

## Q006 请介绍一个你做过的前端项目并说明你的核心贡献

### 元数据
- 岗位：Web前端开发工程师
- 题型：项目深挖
- 主题：项目
- 难度：中级
- 关键词：`项目经历` `职责` `难点` `指标` `复盘`

### 面试题
请介绍一个你做过的前端项目，并重点说明你的核心贡献、难点和最终结果。

### 标准回答
这类问题回答时，建议围绕项目背景、业务目标、个人职责、关键难点、解决方案和结果复盘展开。比如可以先说明项目服务的业务场景和核心目标，再明确自己负责的模块范围，例如页面架构、组件封装、性能优化或工程化建设。然后重点讲一个真正体现个人价值的难点，例如首屏性能问题、复杂表单交互、组件复用混乱或接口状态管理复杂，并说明自己是如何分析问题、设计方案、推动落地以及验证结果的。最后最好给出结果指标，比如加载耗时下降、复用率提升、线上问题减少或交付效率提升，这样会更有说服力。

### 追问点
- 这个项目里你负责的边界是什么？
- 如果再做一次，你会优先重构哪一块？
- 你如何证明这个优化真的有效？

### 评分点
- 回答结构完整，能体现个人贡献
- 不只是介绍业务，还能讲清技术难点和解决方案
- 最好能给出结果或量化指标

### 常见失分点
- 全程都在讲团队做了什么，没有个人贡献
- 没有难点、没有结果、没有复盘
